データ収集バッチ

GitHub Actions 無料（publicリポジトリ）
  • TypeScript で実装（collect.ts）
  • Cron スケジュール実行：毎日 JST 02:00（UTC 17:00）
  • 最大6時間/ジョブ（timeout-minutes: 360）
  • 環境変数：TARGET_REGIONS（デフォルト jp1、現在1リージョンのみ対応）/ TARGET_TIERS（試合を集める対象のランク。PLATINUM / EMERALD / DIAMOND / MASTER のカンマ区切り。未指定時は4ランクすべて。Actions の既定値は当面 PLATINUM）/ MAX_DURATION_MINUTES（デフォルト 330分）/ MAX_MATCHES（未指定時は上限なし）。手動実行では入力欄 max_matches・max_duration_minutes で MAX_MATCHES・MAX_DURATION_MINUTES を指定できる（空なら既定値。定期実行は既定値。v1.9.0 で追加。運用テストなどで短く終えるため）。max_duration_minutes は 330 以下にする（スクリプトは正の整数かどうかしか見ない。時間上限は起動から測るので、330 を超えると、書き込みを終える前に timeout-minutes 360 で打ち切られるおそれがある。360 以上なら必ず打ち切られる。打ち切られると、その回に集めた試合はすべて失われ、running の行が残る）
  • Riot APIキーは GitHub Secrets で管理
  • レート制限ハンドラー内蔵（100 req/2分 → 1200ms sleep制御）
  • 同時実行防止：Concurrency group「collect-daily」で1ジョブずつ実行（cancel-in-progress: false）。同時実行により同じ試合を二重加算しようとして片方の書き込みが全体取り消しされることを防止

Riot Games 公式API

External 無料（Personal API Key。v1.7.1 で Development Key から変更）
  • LEAGUE-V4 /lol/league/v4/entries/RANKED_SOLO_5x5/{tier}/{division}?page={n}: Platinum〜Diamond の段階ごとのプレイヤー一覧（1ページ約205人）。名簿の作成に使う
  • LEAGUE-V4 /lol/league/v4/{challenger|grandmaster|master}leagues/by-queue/RANKED_SOLO_5x5: Master 以上のリーグ全員（上の entries は Master 以上に対応していないため）
  • 名簿（Platinum 以上の全プレイヤーのランク）の作成: JP で約12万人・約600リクエスト・約14分（2026-11-02 計測）
  • MATCH-V5 /lol/match/v5/matches/by-puuid/{puuid}/ids?queue=420&count=20: プレイヤーの直近の試合ID（ソロランクのみ・20件）
  • MATCH-V5 /lol/match/v5/matches/{matchId}: 試合詳細（参加者のチャンピオン・teamPosition・勝敗・アイテム・gameVersion）
  • ホスト: LEAGUE-V4 はプラットフォーム（jp1.api.riotgames.com）、MATCH-V5 はルーティング（asia.api.riotgames.com）。対応: jp1・kr → asia／na1 → americas／euw1・eune1 → europe
  • レート: 20 req / 秒・100 req / 2分 → リクエスト間隔 1.2秒。429 は指数バックオフ（1s → 2s → 4s → 8s）
  • エラーの判定（v1.7.0 で明記）: 429 かどうかは HTTP のステータスコードで判定する（エラーメッセージには URL が入り、試合IDに "429" を含むことがあるため、文字列では判定しない）。429 は最大4回再試行し、5回続いたらステータスコード 429 のエラーにする。429 以外（404・500 など）は再試行せず、そのステータスコードのエラーにする。エラー文に入れる URL のプレイヤーID（PUUID）は先頭8文字だけにする（v1.10.0。公開リポジトリの GitHub Actions のログは誰でも読めるため）。1回の呼び出しは10秒で時間切れにし（応答の本文を読み終えるまで）、時間切れも再試行せずエラーにする（v1.8.0 で追加。応答が止まると時間上限の確認に進めず、システムテスト ST-04 で 17分の上限に対して 31分動いたため）
  • APIキー有効期限: なし（Personal Key。以前の Development Key は24時間で失効し、手動更新が必要だった）。Personal Key は一般公開の製品には使えない（01 制約事項）

データフロー詳細

3.1 バッチ収集フロー（スノーボール方式 / GitHub Actions）

1

起動時準備（APIキー検証・パッチ取得・champions同期）

① Riot APIキーの有効性を検証。
② Data Dragon CDN から最新パッチを自動取得（versions.json の先頭要素を正規化）。
③ Data Dragon から最新チャンピオン一覧を取得し champions テーブルへ UPSERT（FR-24）。新チャンピオン追加・パッチ更新時も自動対応。

2

collection_logs にジョブ開始を記録

collection_logs テーブルに status: 'running' で行を INSERT し、採番された id（BIGSERIAL）を保持。その後のループ終了時・エラー発生時にこの id で UPDATE する。開始ログの INSERT・UPDATE に失敗しても、警告を出してバッチは続ける（v1.9.0 で明記。未決事項 Q-5 の決定。ログのためにその日の収集を止めないため）。
開始ログの後、DB 関数 archive_old_patches() で古いパッチを整理する（v1.10.0 で追加。01 FR-23）。今のパッチより古いパッチ（パッチは数字として比べる）について、item_build_stats と processed_matches を消す（直前のパッチの分も消す。アイテムビルドは1パッチ約550〜840MB の見込みのため。下のコスト試算。テスト仕様書の未決事項 Q-9 の決定。なお v1.10.0 からアイテムビルドは書き込んでいないので、消すのは主に処理済みの試合ID）。champion_stats・counter_stats は残す。1回の呼び出しで消すのは最大2万行で、0行になるまで繰り返す（API の時間の上限 8秒に収めるため。ローカルで30万行を消したとき、1回は最大0.18秒だった。2026-11-10 計測）。失敗したらエラー終了（failed）。

3

名簿を作成（LEAGUE-V4）

LEAGUE-V4 で JP の Platinum 以上の全プレイヤーのランク（puuid → ランク）を取得し、メモリ上に名簿を作る（約14分）。一部のページの取得に失敗しても続行し、その人たちは名簿にいない扱いになる（失敗が20回を超えたら中止）。名簿は試合の平均ランクの計算と、シードの選択に使う。

4

processed_matches から処理済み試合IDを全件取得

processed_matches テーブルからパッチに該当する処理済み試合IDをすべて取得（Supabase PostgREST の1回1000件上限に対応するため、ページ単位で繰り返し取得）。このセットはループ内で処理済み判定に使用。

5

スノーボールメインループ

各イテレーション先頭で終了条件を判定。以下のうち先に達した方で終了：
① 時間上限（MAX_DURATION_MINUTES、デフォルト330分。起動からの経過で、ループの1回ごとの始めに判定する。名簿の作成など、ループに入る前の処理の間は判定しない（上限が名簿の作成より短くても、名簿の作成は最後まで行う）。ループに入った後は1回分だけ超えることがある。1回の Riot API の呼び出しは10秒で時間切れになり、429 の再試行を含めても1回は最大約71秒。v1.8.0 で明記）
② 試合数上限（MAX_MATCHES、未指定なら上限なし）
③ キュー枯渇（収集対象のすべてのランクで、キューも名簿の未使用プレイヤーも尽きた）
キューは収集対象のランク（TARGET_TIERS）ごとに持つ。空になったランクには、名簿からまだ使っていないプレイヤーを5人ずつ補充する。
時間上限と試合数上限に同時に達したときの終了理由は時間上限とする。集めた試合数が同じランクが複数あるときは、低いランクを先に進める（v1.9.0 で明記。テスト仕様書の未決事項 Q-2・Q-6 の決定）。ループ内の処理：集めた試合数が最も少ないランクを選ぶ → そのランクの試合IDキューが空ならプレイヤーの直近20試合のIDを取得し、processed_matches と queuedMatchIds で重複除外して追加 → 試合詳細を取得 → パッチが不一致ならスキップし、そのプレイヤーの残りの試合も取りに行かない（試合IDは新しい順のため残りも古い。休止中のプレイヤーでリクエストを無駄にしないため） → リメイクの試合（参加者の gameEndedInEarlySurrender が true）と、勝者が1チームでない試合（勝った参加者がちょうど5人で同じチームでない。不正対策による中止 endOfGameResult: Abort_AntiCheatExit などで両チームとも負けの試合。v1.10.0 で追加。ST-10 で 1,100試合中1試合）はスキップする。集計せず、processed_matches にも記録せず、参加者を次のシードにも使わない。記録しないため、後の実行で同じ試合IDが返ると試合詳細をもう一度取りに行く。むだは1回の実行につき1回の呼び出し（同じ実行の中では二度取りしない。その試合が誰かの直近20試合に入っている間は、実行のたびに1回ずつ起きる）なので許容する（v1.9.0 で明記。未決事項 Q-7 の決定）。同じプレイヤーの残りの試合は続ける（v1.6.0 で追加。FR-21） → 参加者10人の平均ランクからランク帯を決め、当てはまるランク帯すべてにメモリ上で集計 → 参加者のうち名簿にいて収集対象ランクの人を、未訪問ならそのランクのキューに追加。

6

Supabaseへ加算書き込み（DB関数apply_batch_result）

ループの途中で、新しく処理した試合が 500試合 たまるたびに書き込み、ループ終了後に残りを書き込む（v1.10.0 で変更。以前はループ終了後に1回だけ書き込んでいた）。書き込んだ分の集計はメモリから消す。新しく処理した試合が0件なら書き込まない。理由: API には8秒の時間の上限（authenticator の statement_timeout）があり、330分で集まる試合（ST の計測から1日約9,500〜12,700試合の見込み）をまとめて書き込むと、6,000試合分でもローカルで8.8秒かかった（2026-11-10 計測。1,000試合で約2.0秒、3,000試合で約4.7秒）。また、途中で止まってもそこまでの試合が残る。
書き込みが失敗したらそこで止めてエラー終了（failed）する（DB の障害など、続けても失敗し続ける原因が多いため）。それまでに書き込んだ分は DB に残り、失敗した分の試合は処理済みにならないので、次の実行で取り直せる。
item_build_stats には書き込まない（DB に送るアイテムビルドの行は空。v1.10.0。アイテムビルドを使う機能がまだなく、今のパッチの分だけでも 500MB を超えるおそれがあるため。06 の未決事項 Q-9。集計の仕組みと表は残し、使う機能を作るときに設計し直す）。
集計結果は DB 関数 apply_batch_result() で書き込む。この関数は1回の呼び出しごとに、以下を1トランザクション内で実行：
① processed_matches から処理済み試合をチェック。1件でも含まれていたらエラーで全体を ROLLBACK（同時実行時の二重加算を防止）。
② processed_matches に新規処理試合IDを INSERT。
③ champion_stats / counter_stats / item_build_stats の既存行（行ごとに rank_tier を持つ）に games_played / wins を加算し、win_rate を再計算。新規行は INSERT。
実行権限：service_role キーのみ（GitHub Actions 環境から）。

7

collection_logs をジョブ完了で UPDATE

ループ終了時・エラー発生時に、ステップ2で保持した id で UPDATE。status を 'completed' または 'failed' に、matches_collected を DB に書き込み終えた試合数に（v1.10.0 で変更: 失敗時も、それまでに書き込んだ試合数を記録する。少しずつ書き込むので、失敗しても途中までの試合が残るため。以前は「完了時のみ。失敗時は NULL のまま」。書き込みの応答が届く前に接続が切れた場合は、DB では確定していてもバッチは失敗として数えないので、実際より少なくなることがある）、completed_at を現在時刻に（失敗時も記録し、失敗までの所要時間がわかるようにする）、エラー時は error_message を記録。DB に届かないまま失敗したときは failed への更新もできず、行は running のまま残る（次回の実行は止まらない）。started_at から6時間（timeout-minutes）を過ぎた running の行は、途中で終わった実行とみなす（v1.9.0 で明記。未決事項 Q-5 の決定。めったに起きないため、自動で直す処理は作らない）

書き込むのは勝率（champion_stats）と対面勝率（counter_stats）で、過去のパッチも残す。対面勝率は 1,100試合で 10,048行・2.4MB（ST-10。1行約240バイト）。行数はチャンピオンの組み合わせの数で頭打ちになり、上限はおよそ 170×169×5レーン×4ランク帯 ≒ 57.5万行なので、1パッチの上限は約140MB。最悪の場合は約3パッチ（約6週間）で 400MB に届く。実際は出てこない組み合わせが多いので小さくなる見込みだが、1パッチ（約14〜18万試合）での行数は計測していない。勝率は1パッチ数千行で小さい。処理済みの試合ID は今のパッチの分だけ残り（古いパッチは消す）、1パッチ約14〜18万行・1行約160バイト（ST-10: 1,100行で 176KB）で約30MB が上限。本番の DB の使用量が 400MB を超えたら、古いパッチの対面勝率を消すか、有料プランにするかを決める（定期実行を始めた後は、OT と合わせて使用量を確かめ、1パッチ分の対面勝率の実際の大きさを測る）。
