GitHub Actions での定期実行を始める前に、データ収集バッチが設計書どおりに動き、DB の集計データを壊さないことを確かめる。

対象外画面・API Routes（03・05 の範囲）／Riot API・Supabase 自体の動作

テスト方針

2.1 期待結果の決め方

期待結果は設計書から決め、各項目に根拠（設計書番号と節）を書く。コードから期待結果を書くと、コードの誤りもそのまま正しい結果として扱われてしまうため。設計書に書かれていない動きは、8章「未決事項」に分けて扱う。

2.2 テストの段階

段階確かめること方法・環境記号
単体（UT）計算・変換・判定・メインループの分岐vitest。Riot API と Supabase は偽物に差し替える既存 自動テストあり（テスト名を記載）／追加 自動テストを追加する
結合（IT）DB関数・権限・RLS・ページングローカルの Supabase（3章）に SQL や supabase-js で直接実行手動 手順に沿って実施し、結果を記録する
システム（ST）バッチ全体を1回通したときの結果本物の Riot API ＋ ローカルの Supabase。MAX_MATCHES で試合数を小さくする
運用（OT）GitHub Actions 上での実行main へマージ後、workflow_dispatch で手動実行。本番の Supabase に書き込む

2.3 使うテスト技法

技法このバッチで使う箇所
同値分割環境変数（正しい値・未指定・不正な値）、teamPosition の種類、試合の種類（対象パッチ・古いパッチ・リメイク・勝者が1チームでない試合・処理済み）
境界値分析境界の「1つ下・ちょうど・1つ上」を必ずテストする。平均ポイント 1600・2400・2800、LP の上限 99・400、名簿の取得失敗 20回、429 のリトライ 4回、MAX_MATCHES、PostgREST の 1000件
デシジョンテーブル終了条件（時間・試合数・キュー切れ）の組み合わせ、試合の加算先ランク帯
状態遷移collection_logs.status（running → completed／running → failed）
エラー推測APIキーの失効、429、Riot の 5xx、Supabase の停止、champions にないチャンピオン、同時実行
不変条件の確認正しい答えを1つずつ用意しにくいシステムテストでは、「必ず成り立つ関係」（7章）を SQL で確認する

2.4 優先度

集計は加算方式なので、一度壊れたデータは後から直せない。データの壊れにつながる項目を最優先にする。

優先度内容
P1データの正しさ: 二重加算・パッチの混在・ランク帯の振り分け・加算と勝率の計算・書き込みの取り消し
P2止まり方と異常時: 終了条件・API エラー・環境変数の不正・実行ログ
P3運用: 所要時間・ログの見やすさ・GitHub Actions の設定

定期実行を始める条件: P1・P2 がすべて合格していること。P3 の不合格は、内容を確認して対応を決める。

2.5 期待結果と判定の書き方（v1.3.0 で追加）

「別の理由で失敗したのに合格になる」項目を作らないためのルール。v1.2.0 までの DB-06・07・09 は、どんなエラーでも合格になる判定になっていた（期待結果に「エラーになる」としか書いていない、またはテストが書いてある種類を見ていなかった）。

No.ルール
A-1期待結果は観測できる値で書く。エラーは種類を見分けられる値まで書く: DB は SQLSTATE（例: 23503）、HTTP はステータスコード、バッチは終了コード・メッセージに含む語・出力先（標準出力か標準エラー出力か。02「エラー時の動き」）。同じエラーコードが別の原因でも出る場合（例: 42501 は関数の実行権限がないときと RLS の拒否の両方で出る）は、メッセージまで書いて見分ける。「エラーになる」「エラー終了」だけの書き方はしない
A-2異常系は「どこで止まるか」まで書く。書き込みの取り消しを確かめる項目は、書き込んだ後に失敗する入力を選ぶ（書き込む前に止まる入力では、取り消しを確かめられない）
A-3「判定方法」列に、何と何を比べて合否を決めるかを書く。空欄は「期待結果に書いた値と一致するか」で判定する意味。エラー・取り消し・権限・実行前後の比較・件数の確認は、空欄にしない。ST・OT・手動の項目も同じ
A-4作るときに「関係のない理由で合格にならないか」を見直す。異常系の項目ごとに、別の原因のエラー（引数の誤り・接続できないなど）でも合格になってしまわないかを確かめる
A-5エラーの種類の根拠も設計書にする。設計書に書かれていなければ、テスト仕様書だけで決めず、設計書（02・04・05）に書き足すか、8章の未決事項にする
A-6手動・ST・OT の項目は、再現できる手順を書く。「〜などで」で済ませず、その状態を作る具体的な操作（環境変数・SQL・コマンド）を書く
A-7自動テストで確かめる範囲が一部だけなら、その範囲を書く。残りをどこで確かめるか（または確かめていないこと）も書く
A-8項目どうしの依存は前提に書く。前の項目で作ったデータを使う場合は、その項目IDとデータを書く
A-9近似値と比べる場合は、許容差を数値で書く。「≒」「差が大きい場合」だけにしない
B-1テストは期待結果の要素を1つずつ判定する。「何かエラーが出たか」で済ませない（エラーの種類・メッセージ・回数・前後の値をそれぞれ確かめる）
B-2判定を書いたら、わざと失敗させて NG になることを確かめる。例: 権限エラーの項目を権限のある鍵で実行する、期待するエラーとは別の原因で失敗させる。合格してしまったら判定が甘い。対象は、自動テストと it:db で判定するエラー・権限・取り消しの項目（ST・OT は本番に近い環境で状態を作りにくいため、手順の中で期待と違う状態にならないかを見る）

v1.3.0 で B-2 を実施した内容（すべて NG・失敗になることを確認）: DB-09・10・11 を service_role の鍵で実行／DB-06 を型の誤り（22P02）で失敗させる／DB-07 を lane の長さ超過（22001）で失敗させる／実装の HTTP エラーのステータスを常に 500 にする（API-04・05）／TARGET_TIERS のメッセージを変える（ENV-07）／メッセージから変数名を外す（ENV-09・10・12）／SUPABASE_URL・RIOT_API_KEY の確認を外す（ENV-13・14）。DB-06・07 の2つは、v1.2.0 の最初の判定（「何かエラーが出たか」だけを見る）なら合格していた。test-design-reviewer の指摘を受けて、さらに DB-09 を anon に実行権限を与えた状態で実行（エラーコードだけの判定では合格していたため、メッセージも見るように変更）・DB-11 のバッチ専用テーブルへの INSERT を service_role で実行し、どちらも NG になることを確認
