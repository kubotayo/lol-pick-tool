目的と範囲

GitHub Actions での定期実行を始める前に、データ収集バッチが設計書どおりに動き、DB の集計データを壊さないことを確かめる。

区分内容
対象FR-20（スノーボール収集）・FR-21（集計と加算）・FR-22（実行ログ）・FR-24（champions 同期）、非機能要件のセキュリティ（キーの管理）、02「バッチ収集フロー」ステップ1〜7、04 の変換ルール・DB関数・RLS
対象外画面・API Routes（03・05 の範囲）／FR-23 パッチ更新時の自動アーカイブ（未実装）／Riot API・Supabase 自体の動作
2

テスト方針

2.1 期待結果の決め方

期待結果は設計書から決め、各項目に根拠（設計書番号と節）を書く。コードから期待結果を書くと、コードの誤りもそのまま正しい結果として扱われてしまうため。設計書に書かれていない動きは、8章「未決事項」に分けて扱う。

2.2 テストの段階

段階確かめること方法・環境記号
単体（UT）計算・変換・判定・メインループの分岐vitest。Riot API と Supabase は偽物に差し替える既存 自動テストあり（テスト名を記載）／追加 自動テストを追加する
結合（IT）DB関数・権限・RLS・ページングローカルの Supabase（3章）に SQL や supabase-js で直接実行手動 手順に沿って実施し、結果を記録する
システム（ST）バッチ全体を1回通したときの結果本物の Riot API ＋ ローカルの Supabase。MAX_MATCHES で試合数を小さくする
運用（OT）GitHub Actions 上での実行main へマージ後、workflow_dispatch で手動実行。本番の Supabase に書き込む

2.3 使うテスト技法

技法このバッチで使う箇所
同値分割環境変数（正しい値・未指定・不正な値）、teamPosition の種類、試合の種類（対象パッチ・古いパッチ・リメイク・処理済み）
境界値分析境界の「1つ下・ちょうど・1つ上」を必ずテストする。平均ポイント 1600・2400・2800、LP の上限 99・400、名簿の取得失敗 20回、429 のリトライ 4回、MAX_MATCHES、PostgREST の 1000件
デシジョンテーブル終了条件（時間・試合数・キュー切れ）の組み合わせ、試合の加算先ランク帯
状態遷移collection_logs.status（running → completed／running → failed）
エラー推測APIキーの失効、429、Riot の 5xx、Supabase の停止、champions にないチャンピオン、同時実行
不変条件の確認正しい答えを1つずつ用意しにくいシステムテストでは、「必ず成り立つ関係」（7章）を SQL で確認する

2.4 優先度

集計は加算方式なので、一度壊れたデータは後から直せない。データの壊れにつながる項目を最優先にする。

優先度内容
P1データの正しさ: 二重加算・パッチの混在・ランク帯の振り分け・加算と勝率の計算・書き込みの取り消し
P2止まり方と異常時: 終了条件・API エラー・環境変数の不正・実行ログ
P3運用: 所要時間・ログの見やすさ・GitHub Actions の設定

定期実行を始める条件: P1・P2 がすべて合格していること。P3 の不合格は、内容を確認して対応を決める。

項目内容

ローカルの Supabase の準備

# 初回のみ: supabase/config.toml を作る
npx supabase init

# 起動すると supabase/migrations/ の 001〜005 が順に適用される
npx supabase start

# 表示される API URL と service_role key を控える
npx supabase status

# バッチの実行（.env.local は読まれないため、環境変数は実行時に渡す）
SUPABASE_URL=http://127.0.0.1:54321 \
SUPABASE_SERVICE_ROLE_KEY=<ローカルの service_role key> \
RIOT_API_KEY=<当日の Development Key> \
TARGET_TIERS=PLATINUM MAX_MATCHES=10 \
npm run collect

# DB を初期状態に戻す（migration を適用し直す）
npx supabase db reset
# 結合テスト DB-01〜11 を実行する（初期状態に戻してから実行し、項目ごとに OK／NG を出す）
npm run it:db
ST はどれも名簿の作成に約14分かかる（02 ステップ3）。1回の ST は 15〜20分程度を見込む。

不変条件の確認 SQL

1試合ごとの正解を用意しにくい ST・OT では、「設計どおりなら必ず成り立つ関係」を確認する。SQL-2〜6 は、該当する行が 0件 なら合格。:patch は対象パッチに置き換える。

-- SQL-1: ランク帯ごとの試合数（標準出力の「ランク帯別の加算試合数」と比べる）
-- champion_stats はレーンがある参加者全員を加算する（相手の有無は問わない）。勝ったチームでレーンがある人は通常5人なので、wins の合計 ÷ 5 ≒ 試合数
SELECT rank_tier, SUM(wins) / 5.0 AS approx_matches, SUM(games_played) AS player_games
FROM champion_stats WHERE patch = :patch GROUP BY rank_tier ORDER BY rank_tier;

-- SQL-2: win_rate が wins / games_played と一致しない行
SELECT * FROM champion_stats
WHERE patch = :patch AND ABS(win_rate - ROUND(wins::numeric / games_played, 4)) > 0.0001;
-- counter_stats・item_build_stats も同様

-- SQL-3: wins が games_played を超える、または 0 以下の games_played
SELECT * FROM champion_stats WHERE patch = :patch AND (wins > games_played OR games_played <= 0);

-- SQL-4: ランク帯の包含関係が崩れている行（上のランク帯の試合数が下のランク帯を超える）
-- master_plus ⊂ diamond_plus ⊂ platinum_plus ⊂ all
SELECT a.champion_id, a.lane, a.rank_tier, a.games_played, b.rank_tier, b.games_played
FROM champion_stats a
JOIN champion_stats b USING (champion_id, lane, patch, region)
WHERE a.patch = :patch
  AND ((a.rank_tier, b.rank_tier) IN (('master_plus','diamond_plus'), ('diamond_plus','platinum_plus'), ('platinum_plus','all')))
  AND a.games_played > b.games_played;
-- 上のランク帯にだけ行があり、下のランク帯に行がない場合も不合格（LEFT JOIN で確認）
SELECT a.champion_id, a.lane, a.rank_tier, a.games_played, t.lower_tier
FROM champion_stats a
JOIN (VALUES ('master_plus','diamond_plus'), ('diamond_plus','platinum_plus'), ('platinum_plus','all')) AS t(upper_tier, lower_tier)
  ON a.rank_tier = t.upper_tier
LEFT JOIN champion_stats b
  ON b.champion_id = a.champion_id AND b.lane = a.lane AND b.patch = a.patch AND b.region = a.region AND b.rank_tier = t.lower_tier
WHERE a.patch = :patch AND b.id IS NULL;

-- SQL-5: counter_stats の対称性が崩れている組（A 対 B と B 対 A は同じ試合数で、勝ち数の合計は試合数）
SELECT a.champion_id, a.enemy_champion_id, a.lane, a.rank_tier
FROM counter_stats a
LEFT JOIN counter_stats b
  ON b.champion_id = a.enemy_champion_id AND b.enemy_champion_id = a.champion_id
 AND b.lane = a.lane AND b.patch = a.patch AND b.region = a.region AND b.rank_tier = a.rank_tier
WHERE a.patch = :patch
  AND (b.id IS NULL OR a.games_played <> b.games_played OR a.wins + b.wins <> a.games_played);

-- SQL-6: 対象パッチ以外のデータが混ざっている（今回の実行で別パッチの行が増えていないか）
SELECT patch, COUNT(*) FROM champion_stats GROUP BY patch;
SELECT patch, COUNT(*) FROM processed_matches GROUP BY patch;
SQL-1 の「≒」: 勝ったチームに teamPosition が空の参加者がいる試合があると、5 で割った値は実際の試合数より少し小さくなる（v1.0.1 で理由の説明を修正）。差が大きい場合は原因を調べる。
