Riot API の値からの変換

カラム変換ルール
lane試合詳細の teamPosition を変換する: TOP → TOP／JUNGLE → JG／MIDDLE → MID／BOTTOM → BOT／UTILITY → SUP。それ以外（空文字など）の参加者は集計しない
regionプラットフォーム名から数字を除いて大文字にする（例: jp1 → JP、euw1 → EUW）
patchgameVersion の先頭2つ（例: 14.21.619.9898 → 14.21）
（対象外の試合）リメイク（参加者の gameEndedInEarlySurrender が true）の試合（v1.6.0 で追加）と、勝者が1チームでない試合（v1.9.0 で追加）は、どの集計テーブルにも加算せず、processed_matches にも記録しない（01 FR-21）
rank_tier_plus が付く値はそのランク以上をすべて含む（例: diamond_plus = Diamond・Master・Grandmaster・Challenger）。all は収集したすべての試合。
試合のランク帯は参加者10人の平均ランクで決め、当てはまるランク帯すべてに加算する（例: 平均 Diamond の試合 → all・platinum_plus・diamond_plus の3行に加算）。
平均の出し方: ランクをポイントにして平均する。Iron IV 0LP を 0 とし、1段階 100・1ランク 400（Platinum IV = 1600、Emerald IV = 2000、Diamond IV = 2400、Master = 2800）。段階内の LP は 99 まで足す。Master 以上は 2800 + LP（LP は 400 で打ち切る。1人の高い LP が平均を大きく動かさないため）。LP が負の値なら 0LP として扱う（v1.8.0 で明記。テスト仕様書の未決事項 Q-3 の決定）。名簿（Platinum 以上）にいない人は Gold II 50LP 相当（1450）として平均に入れる（外すと実際より高いランクの試合として数えられるため）。
判定: 平均 1600 以上 → platinum_plus／2400 以上 → diamond_plus／2800 以上 → master_plus。ランクは試合時点ではなくバッチ実行時点のもの

-- champions (マスターテーブル)
CREATE TABLE champions (
  champion_id   INTEGER       PRIMARY KEY,
  champion_key  VARCHAR(50)   NOT NULL UNIQUE,
  champion_name VARCHAR(100)  NOT NULL,
  image_url     TEXT,
  created_at    TIMESTAMPTZ   NOT NULL DEFAULT now(),
  updated_at    TIMESTAMPTZ   NOT NULL DEFAULT now()
);

-- champion_stats (先出しピック用集計)
CREATE TABLE champion_stats (
  id            BIGSERIAL     PRIMARY KEY,
  champion_id   INTEGER       NOT NULL REFERENCES champions(champion_id),
  lane          VARCHAR(5)    NOT NULL,
  patch         VARCHAR(20)   NOT NULL,
  region        VARCHAR(10)   NOT NULL,
  rank_tier     VARCHAR(20)   NOT NULL,
  games_played  INTEGER       NOT NULL DEFAULT 0,
  wins          INTEGER       NOT NULL DEFAULT 0,
  win_rate      DECIMAL(5,4)  NOT NULL DEFAULT 0,
  updated_at    TIMESTAMPTZ   NOT NULL DEFAULT now(),
  UNIQUE (champion_id, lane, patch, region, rank_tier)
);
CREATE INDEX idx_stats_filter ON champion_stats (lane, patch, region, rank_tier);

-- counter_stats (カウンターピック用対戦統計)
CREATE TABLE counter_stats (
  id                BIGSERIAL     PRIMARY KEY,
  champion_id       INTEGER       NOT NULL REFERENCES champions(champion_id),
  enemy_champion_id INTEGER       NOT NULL REFERENCES champions(champion_id),
  lane              VARCHAR(5)    NOT NULL,
  patch             VARCHAR(20)   NOT NULL,
  region            VARCHAR(10)   NOT NULL,
  rank_tier         VARCHAR(20)   NOT NULL,
  games_played      INTEGER       NOT NULL DEFAULT 0,
  wins              INTEGER       NOT NULL DEFAULT 0,
  win_rate          DECIMAL(5,4)  NOT NULL DEFAULT 0,
  updated_at        TIMESTAMPTZ   NOT NULL DEFAULT now(),
  UNIQUE (champion_id, enemy_champion_id, lane, patch, region, rank_tier)
);
CREATE INDEX idx_counter_enemy ON counter_stats (enemy_champion_id, lane, patch, region, rank_tier);

-- processed_matches (スノーボール方式の重複除去・バッチ実行をまたいだ処理済み管理)
CREATE TABLE processed_matches (
  match_id      VARCHAR(30)   PRIMARY KEY,
  patch         VARCHAR(20)   NOT NULL,
  processed_at  TIMESTAMPTZ   NOT NULL DEFAULT now()
);
CREATE INDEX idx_processed_patch ON processed_matches (patch);

-- apply_batch_result 関数（v1.4.0 で追加、v1.5.0 で p_rank_tier を廃止し各行が rank_tier を持つ形に変更。005 マイグレーション）
-- 集計結果の加算書き込みを1トランザクション内で実行。1試合が複数のランク帯に加算されるため、ランク帯は行ごとに渡す
CREATE OR REPLACE FUNCTION apply_batch_result(
  p_patch         text,
  p_region        text,
  p_champion_rows jsonb,   -- [{champion_id, lane, rank_tier, games_played, wins}]
  p_counter_rows  jsonb,   -- [{champion_id, enemy_champion_id, lane, rank_tier, games_played, wins}]
  p_item_rows     jsonb,   -- [{champion_id, lane, item_ids, rank_tier, games_played, wins}]
  p_match_ids     text[]
) RETURNS void
LANGUAGE plpgsql
SECURITY INVOKER
AS $$
DECLARE
  v_duplicates text[];
BEGIN
  -- 処理済み試合が含まれていないか確認
  SELECT array_agg(match_id) INTO v_duplicates
  FROM processed_matches
  WHERE match_id = ANY(p_match_ids);

  IF v_duplicates IS NOT NULL THEN
    RAISE EXCEPTION '処理済みの試合が % 件含まれています', array_length(v_duplicates, 1);
  END IF;

  -- processed_matches へ記録（重複チェック）
  INSERT INTO processed_matches (match_id, patch)
  SELECT unnest(p_match_ids), p_patch;

  -- champion_stats に加算
  INSERT INTO champion_stats AS t (...) VALUES (...)
  ON CONFLICT (...) DO UPDATE SET
    games_played = t.games_played + EXCLUDED.games_played,
    wins         = t.wins + EXCLUDED.wins,
    win_rate     = (t.wins + EXCLUDED.wins)::numeric / (t.games_played + EXCLUDED.games_played);

  -- counter_stats / item_build_stats も同様に加算
END $$;

-- apply_batch_result 実行権限: service_role のみ
REVOKE ALL ON FUNCTION apply_batch_result(...) FROM PUBLIC, anon, authenticated;
GRANT EXECUTE ON FUNCTION apply_batch_result(...) TO service_role;

-- archive_old_patches 関数（v1.9.0 で追加。006 マイグレーション）
-- 今のパッチより古いパッチの item_build_stats・processed_matches を、1回に最大 p_limit 行消す（01 FR-23）
-- champion_stats・counter_stats は残す。パッチは数字の配列にして比べる（'16.9' < '16.10'）。戻り値は消した行数
CREATE INDEX idx_item_build_patch ON item_build_stats (patch);
CREATE OR REPLACE FUNCTION archive_old_patches(p_current_patch text, p_limit integer DEFAULT 20000)
RETURNS integer LANGUAGE plpgsql SECURITY INVOKER ...
  -- 消す対象: champion_stats ∪ processed_matches にあるパッチのうち、今のパッチより古いもの
  DELETE FROM item_build_stats WHERE id IN (SELECT id ... WHERE patch = ANY(古いパッチ) LIMIT p_limit);
  -- 残りの枠で processed_matches も同様に消す
REVOKE ALL ON FUNCTION archive_old_patches(text, integer) FROM PUBLIC, anon, authenticated;
GRANT EXECUTE ON FUNCTION archive_old_patches(text, integer) TO service_role;

Row Level Security（RLS）方針

項目内容
RLS設定 全テーブル有効（セキュリティアドバイザーの推奨により有効化）
ポリシー詳細 画面表示用4テーブル（champions / champion_stats / counter_stats / item_build_stats）： anon_select_<テーブル名> ポリシーで anon ロールに SELECT のみ許可（USING (true)）
バッチ専用2テーブル（collection_logs / processed_matches）： ポリシーなし（anon からのアクセス不可）
フロントエンドからの操作 Next.js API Routes（lib/supabase/server.ts）で anon キーを使用し、SELECT のみ実行。INSERT / UPDATE / DELETE はバッチ（GitHub Actions）の service_role キーのみ実行
service_role キーについて service_role キーは Supabase セキュリティモデルで RLS をバイパスする。バッチ専用2テーブルへの書き込みは service_role キーでのみ可能
anon キーで操作したときの結果
（v1.7.0 で明記）		 画面表示用4テーブル: SELECT はできる。INSERT は RLS の拒否（SQLSTATE 42501、メッセージ「new row violates row-level security policy」）。UPDATE・DELETE はエラーにならず対象 0行（UPDATE・DELETE のポリシーがないため）。どの場合もデータは変わらない
バッチ専用2テーブル: SELECT はエラーにならず 0行（ポリシーがないため行が見えない）。INSERT は RLS の拒否（42501）。UPDATE・DELETE はエラーにならず 0行。データは変わらない
archive_old_patches の呼び出し: apply_batch_result と同じく権限エラー（42501、「permission denied for function archive_old_patches」。v1.9.0。06 の DB-14）
apply_batch_result の呼び出し: 権限エラー（42501、メッセージ「permission denied for function apply_batch_result」。実行権限を service_role に限っているため）。同じ 42501 は RLS の拒否でも出る（実行権限の設定が漏れていると、関数の中の INSERT が RLS で拒否されて 42501 になる）ので、テストではメッセージで見分ける
いずれも 2026-11-07 の結合テスト（06 の DB-09〜11）で確認した動き（実行権限の設定漏れのときの動きも、ローカルの DB で anon に実行権限を与えて確認した）
apply_batch_result のエラー
（v1.7.0 で明記）		 処理済みの試合を含む: RAISE EXCEPTION（SQLSTATE P0001）。メッセージは「処理済みの試合が N 件含まれています（バッチの同時実行の可能性）。例: …」。書き込む前に止まる
champions にない champion_id を含む: 外部キー違反（23503）。processed_matches などを書いた後に起きるが、1トランザクションなので全体が取り消される
同時実行で同じ試合IDが後から入った: processed_matches の主キー違反（23505）で全体が取り消される
バッチは500試合ごとにこの関数を呼ぶ（v1.9.0。02 ステップ6）。全体が取り消されるのは、その1回の呼び出しの分だけ
バッチはどのエラーも「[apply_batch_result] 書き込み失敗: <メッセージ>」としてエラー終了する（02「エラー時の動き」）
