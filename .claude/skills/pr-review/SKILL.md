# PR のレビュー

PR を作ったら、次の順で進める。テスト仕様書の PR を作る前の確認（文書全体を 2.5 で見る）は `.claude/rules/test-spec.md` の 2 に従い、これとは別に行う。

## 0. PR を作る前に、自分で抜けを潰す

共通ルール（`~/.claude/CLAUDE.md`）の「作業の後に、自分で確かめる」にある「PR を作る・レビューを頼む前」の項目を確かめる。このプロジェクトでは、それぞれ次を指す。

- 作業ログ: `work-log/CURRENT.md` と当日の `work-log/YYYY/YYYY-MM-DD.md`。マージ済みの PR などが未完了のまま残っていない
- 決まった項目: 当日のログの「やったこと」「決めたこと（とその理由）」「変更したファイル / コミット」
- 設計書のバージョン: ヘッダーのバージョンと「更新内容 (バージョン)」がそろい、ほかの文書が参照するバージョン（06 の「根拠とする設計書」など）も合っている
- 同じことを書いたほかの場所: docs・CLAUDE.md・ワークフローのコメント
- 未確定事項: 仮決めした判断が `docs/factory/<ブランチの短い名前>/open-items.md` にあり、PR の本文に写してある（仮決めがなければ不要。決まりは `CLAUDE.md` の「自動で進める」）

加えて、PR の本文の最後に、Claude Code が指定する署名の行（`🤖 Generated with [Claude Code](https://claude.com/claude-code)`）を入れる。コミットのメッセージの最後には `Co-Authored-By` の行を入れる（文面はそのときの Claude Code の指定に従う）

## 1. reviewer を起動する

1. `gh pr diff <番号> > <スクラッチパッド>/pr<番号>.diff` で差分を保存する
2. メインの作業ツリーが PR のブランチを checkout していない場合は、reviewer がそのブランチの内容を読めるように、スクラッチパッドに `git worktree add` で PR のブランチを置き、そのパスも伝える（reviewer はメインの作業ツリーを読むため。終わったら `git worktree remove` する）
3. `reviewer` に、差分のパスと PR の目的（1〜2文）を渡して起動する。必要なら確認してほしい点も伝える
4. テストの結果列を記入した差分では、どのスクリプト（手動の項目は「判定方法」列）がいつレビュー済みかも伝える

## 2. 指摘を確かめる

- 指摘ごとに、コード・設計書を読んで正しいかを確かめる。reviewer の言い分をそのまま受け入れない
- 「確実な問題」「疑わしい点」のどちらも確かめる

## 3. 直す

- 正しいと確かめた指摘は、同じ PR に追加コミットして直し、PR の説明も更新する
- 仕様や方針の判断が要る指摘は、直さずに未確定事項に残し、5 の報告で選択肢（A案／B案）と推奨案を添えてユーザーに確認する
- 直した内容は、当日の作業ログにも書き足す

## 4. 再レビューするかを決める

| 追加コミットの中身 | 再レビュー |
|---|---|
| コードの動きを変えた | 追加分をもう一度 `reviewer` にかける |
| 文言の修正だけ | しない |
| 自動テスト（vitest）の判定を強めただけ | しない |
| 結果列に記入する項目（`it:db`・`it:browser`・手動）の判定を直した（強めた場合も含む） | する（`.claude/rules/test-spec.md` の 4 に従う。結果はその後に記入する） |

## 5. ユーザーに報告する

次の3つに分けて、短く報告する。

- 直したもの
- 確認したいもの（選択肢と推奨案つき）
- 誤っていた指摘（なぜ誤りか）

ユーザーにマージを頼むのは、レビューと修正が終わった後。レビュー前にマージされた PR も、あとからこの手順でレビューする。PR へのコメント投稿はユーザーの承認後に行う。
