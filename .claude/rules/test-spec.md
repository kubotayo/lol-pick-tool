# テスト仕様書

1. テスト仕様書（`docs/06_batch-test-spec.html` など）の期待結果と判定は、06 の「2.5 期待結果と判定の書き方」（A-1〜A-9・B-1〜B-2）に従う。特に、エラーは種類（SQLSTATE・ステータスコード・終了コード・メッセージ・出力先）まで書き、「エラーになる」だけの書き方をしない
2. テスト仕様書を作成・更新したら、PR を作る前に `reviewer` で確認する。このときはコミットしてから差分（`git diff origin/development...HEAD`）を渡し、差分だけでなく**文書全体を 2.5 のルールで見る**よう頼む（問題は変更していない項目に残っていることが多いため）。PR を作った後の差分の確認（`CLAUDE.md` の「PR のレビュー」）とは別に行う
3. テストの判定を書いたら、わざと失敗させて NG になることを確かめる（B-2）。確かめた内容は作業ログに残す
4. テストの「結果」列は、テストのスクリプト（自動テスト・結合テスト）を `reviewer` が確認した後に記入する。結果を記入した差分をレビューに出すときは、どのスクリプト（手動の項目は「判定方法」列）がいつレビュー済みかを起動時に伝える。結果列に記入する項目（`it:db`・手動）の判定を直したとき（強めた場合も含む。直す対象はスクリプトの判定とテスト仕様書の「判定方法」列の両方）は、直した部分をもう一度 `reviewer` にかけてから記入する（`pr-review` スキルの再レビューの決まりより優先する）

- 理由: 06 の DB-06・07・09 が、どんなエラーでも合格になる判定になっていた。仕様書が期待結果をあいまいに書き、テストもそれを見逃し、レビュー前に「合格」と記入していたため（2026-11-07 にルール化。ユーザーの判断。判定を直したときの再レビューは 2026-11-08 に追加。テスト仕様書の確認は 2026-11-08 に `test-design-reviewer` から `reviewer` にまとめた: リポジトリにあり読み取り専用で、このプロジェクトの前提を持つため。`test-design-reviewer` の指摘が多かったのはエージェントの違いではなく、文書全体を見るよう頼んだためだった）
