# 設計書の更新ルール

- **共通**: 事実（実装済みの内容）を書き、推測や「予定」は書かない／設計判断の理由（Why）を残す／古い仕様の扱いは共通ルールの「文書の本文には今の仕様を書き、経緯は分ける」に従う（このプロジェクトの変更履歴の欄は、ヘッダーの「更新内容 (バージョン)」）／全書き直しより差分更新を優先する
- **バージョン**: 更新した設計書のヘッダーのバージョン番号と日付を上げ、変更概要をヘッダーの「更新内容 (バージョン)」に追記する
- **01 要件定義書**: 要件IDは既存の最大番号の続きから採番する（追加前に既存IDを確認する）。優先度は `Must`（なければリリース不可）／`Should`（重要だが代替手段あり）／`Could`（余裕があれば）。スコープの出し入れは「スコープ外」セクションと「機能要件」の両方を更新する
- **02 システム構成図**: SVGは座標を変えずテキスト変更を優先する。新コンポーネントは「コンポーネント詳細」テーブルにも追加する。コスト試算を実態に合わせる
- **03 画面設計書**: 画面IDは既存の続き（現在 SCR-01〜04）。画面遷移図の既存配置を崩さない。アノテーション番号は画面ごとに1から
- **04 DB設計書**: カラム追加はテーブル定義カードとDDLの両方、テーブル追加はER図・定義カード・外部キー一覧・DDLすべてを更新する。DDLは `supabase/migrations/` と実際に適用したものに一致させる。マスター値が変わったらマスター値一覧も更新する
- **05 API設計書**: パラメーター・既定値・応答の形・エラーを変えたら該当エンドポイントの節を更新する。許可値は `lib/constants.ts` と 04 のマスター値一覧に一致させる。仮実装の項目は「実装状況」の表で状態を管理する
